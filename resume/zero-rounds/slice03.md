# slice03 (crates/runner/src/trade.rs, crates/runner/src/validate.rs) — 2 findings

## F1 [low] `Trade::entry_bar` / `Trade::signal_bar` rustdoc and module rule 2 are wrong for every fill-sourced (reprojected) column, which is the shipping two-series path
- where: crates/runner/src/trade.rs:145-146 (`signal_bar`: "The bar whose close carried the signal. Nothing is traded on it."; `entry_bar`: "always `signal_bar + 1`"), module doc trade.rs:24-26 ("A signal on bar `N` fills on bar `N + 1`")
- what: `walk_core` sets `step = 0` for `Sourced::Fill` (trade.rs:984), so `entry = signal` and the emitted `Trade { signal_bar: signal, entry_bar: entry }` has `entry_bar == signal_bar`. On those columns `signal_bar` is the execution-series fill bar, not the bar whose close carried the signal, and it IS traded on (entry is filled at its open). Every validate.rs two-series door (`walk_forward_projected*`, V2/V3/V4) and cli's projected runs produce exactly these trades. The sibling `Occupancy::signal_bar` doc (trade.rs:200-207) and `cli::trades::Row::entry_bar` (cli/src/trades.rs:142-143) were already corrected; `Trade` was not. A consumer that trusts the public doc to get the signal bar as `entry_bar - 1`, or to compute the hold from `signal_bar`, is off by one bar on every reprojected trade.
- evidence: the module's own test pins the opposite of the doc: trade.rs:1801-1805 `assert_eq!(fill.entry_bar, fill.signal_bar, "and on a fill-sourced column the entry IS the source ...")` in `a_reprojected_column_enters_on_the_bar_it_was_told_to`. Not found in known/*, docs/11-findings.md.
- fix: reword `Trade::signal_bar`/`entry_bar` and rule 2 the way `Occupancy::signal_bar` already says it: `signal_bar + 1` on a same-series (`Sourced::Signal`) column; on a `Sourced::Fill` column `signal_bar` is the execution bar stamped at the signal close and `entry_bar == signal_bar`.

## F2 [low] `fold_rungs` quietly turns a malformed or zero `BRUTEX_GRID_RUNGS` into 4, and its doc says it refuses
- where: crates/runner/src/validate.rs:1667-1676 (called by the legacy door `walk_forward_shaped`, validate.rs:1945, and so by `walk_forward`)
- what: `std::env::var_os(..).and_then(|raw| raw.trim().parse::<usize>().ok()).filter(|&n| n > 0).unwrap_or(DEFAULT_RUNGS)`. `BRUTEX_GRID_RUNGS=0`, `=five`, `=-3` or `=99999999999999999999999` all produce `DEFAULT_RUNGS` (4) with no refusal, no reason and no trace on the returned `Validated`. The doc says "A zero is refused rather than obeyed". What actually happens is a silent replacement, and a typo goes unnoticed in the same way. An operator who set the variable is told nothing when their grid width is ignored, which is the §4 "fallback that hides a failure" shape. The impact is limited because only tests and `runner/tests/end_to_end.rs` reach this legacy door today. The operator-facing doors take an explicit `rungs`.
- evidence (trace): with the env var set to `"0"`, `parse` gives `Some(0)`, `filter(n > 0)` gives `None`, and `unwrap_or` gives `4`. With `"abc"`, `parse` gives `Err`, `.ok()` gives `None`, and the result is again `4`. Neither branch returns an error or sets `Validated::refused`. The only external mention, docs/11-findings.md:353, is about the env-read budget, not this behaviour.
- fix: return `Result<usize, String>` (or `Option` meaning "unset") and have `walk_forward_shaped` set `Validated::refused` when the variable is present but not a positive integer. At minimum, correct the doc to "silently replaced by DEFAULT_RUNGS".
