# o1api: O(1) audit of `crates/api` and `crates/pull` (commit bc53131)

Scope: the per-HTTP-request paths in `api` and the per-record, per-window and per-acquire paths in `pull`.
Docs checked: CLAUDE.md, docs/06-limits.md (§2, §7c, §17, §21, §23, §24, §32, §34, §39, §46, §53, §67, D-0686), docs/11-findings.md, the queue (queued_index.txt and fq/*.md).
One probe was run and then deleted (o1api-44). `git status --porcelain` is empty.

docs/06-limits.md §2 claims three things for the pull: it is **bounded** (a governor), **resumable**, and **honest**. It never claims O(1).
- The governor's arithmetic is O(1) per acquire (row 52).
- "under any concurrency" is still unproven, and §21 says so.

Verdict key: O(1) means constant in every growing quantity. BOUNDED means the work is capped by a constant, but the constant is large or set by input. NOT O(1) means the work grows with store, history or input size.

## Summary of NEW items
- o1api-44 (medium): per-bucket String + warn emit in derived-rung completeness. Measured at 905 diagnostics and 158 KB for 5 days of data after LAST_DAY. It repeats every window × 7 rungs.
- o1api-21 (low): `/audit.json` walks every vendor's entries on every poll; nothing caches it.
- o1api-34 (low): the csv.rs claim "No allocation per row / reserved" is false (csv.rs:563, 588).
- o1api-33 (low): the full `serde_json::Value` tree of a ≤64 MiB body; peak memory unmeasured.
- o1api-54 (low): the governor acquire has no fairness. The api refusal after 64 waits can misstate the cause; the http.rs loop is unbounded.
- o1api-4 / o1api-3 (low): query parsing is O(K·Q), and Q is capped only by hyper's implicit 417,792 B default.
- o1api-39 (trivial doc), o1api-36 (avoidable copy).

Everything else is O(1), bounded and documented, or already QUEUED or DOCUMENTED, as marked.
