# attackdata: adversarial attack on the data path at 1087e54 (store, lake, pull, core, costs, greeks, indicators)

**Verdict.** The data path held up well against extreme inputs. All 8 key findings from the prior pass (probestore-1..7 and probeengine-1) are **FIXED** at HEAD. I re-ran the probes and quote the output below. Six probe files ran 21 tests in total. They covered header attacks, truncated and corrupted files, extreme values at append, re-runs, concurrent writers, a real full disk (ENOSPC, on a 40 KiB tmpfs), a real read-only mount, the catalog, CSV and JSON decoders, the fold, the calendar, the Paisa snap, costs (300k-case fuzz), greeks extremes and the indicators isqrt (about 4M cases). The output had **no panic and no non-finite value accepted**.

I found **one NEW medium defect**, where data can silently disappear. If a committed bar file has been truncated to zero bytes or zeroed back to the header region, `BarFile::open_or_create` re-initialises it as a fresh empty month. It logs nothing, and the `.crc` sidecar that proves records existed is ignored. The read door refuses the same file.

There are also five NEW low or info items:
- A Greek re-run with `-0.0` is reported `AlreadyPresent` although the bytes differ.
- Duplicate JSON keys in a vendor answer are silently resolved last-wins.
- A price text with more than 17 significant digits is snapped through f64 and lands one paisa off the vendor's own text.
- `fold` nets negative snapshot volumes, and `Bucket::of_secs` takes any width.
- `calendar::sessions_between` silently leaves out the unmeasured Muhurat day instead of returning `None`.

Probes were `crates/<crate>/tests/zz_audit_attackdata_<n>.rs`, run after BUILD_DONE and then deleted. `git status --porcelain` is empty at the end. The tmpfs was mounted under the scratchpad and then unmounted.

## Not attacked / UNVERIFIED

- I did not probe lake parquet files beyond confirming the probestore-7 fix exists in source and that its test is named. I wrote no new lake parquet probe, so lake's other paths are UNVERIFIED by me.
- I did not test concurrent writers across processes. Within one process, two `flock` descriptors conflict (`Locked`), which is the same kernel mechanism.
- Partial-write ENOSPC landed on the record write, not on the slot or sidecar write. I did not force a failure at the `.crc` or slot stage.
- The append path admits a bar at 03:00 IST inside the month (`ts 03:00 IST inside month: Ok(Committed …)`). This is DOCUMENTED: docs/06-limits.md D-0915, and the `Admission` doc at file.rs:2735.
