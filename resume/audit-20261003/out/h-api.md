| h-api-1 | medium | api | crates/api/src/server.rs:16900-16921 (`HeadDeadline::observe`) | The head-read deadline (probeapi-1, D-1200) can be turned off by sending two blank lines first. `observe` decides the head has ended on any `\n\n` or `\n\r\n` in the byte stream and switches to `HeadState::Delivered`, which stops the clock. But httparse/hyper skip empty lines that come before the request line, so hyper is still waiting for a head. A client that opens with `\r\n\r\n` and then sends a partial head (or nothing) keeps its connection and its `MAX_CONNECTIONS` slot for as long as it likes. 256 such sockets stop `accept` for good, which is the descriptor-exhaustion DoS D-1200 was meant to close. docs/06-limits.md D-1200 says the deadline covers the whole head and does not mention this bypass. | Probe `crates/api/tests/zz_audit_h_api_1.rs` (deleted), `serve_limited` with a 300 ms deadline. Control: `GET /ok HTTP/1.1\r\nHost: x\r\n` was answered `HTTP/1.1 408 Request Timeout` and closed. Attack: `\r\n\r\nGET /ok HTTP/1.1\r\nHost: x\r\n` printed `PROBE-A leading CRLFs: still open after 10T = true, said=""`, so it was still open with no reply after 10x the deadline. | Ignore CR/LF bytes while no non-CRLF byte of this head has been seen (when `partial` is false, keep `progress` at 0), so only a blank line after real head bytes ends the head. Add a test that sends leading CRLFs and expects a 408. Or end the deadline only when hyper hands the request to the service (a `from_fn` layer that flips a shared flag), not by scanning bytes. |
| h-api-2 | low | api | crates/api/src/ingest.rs:1457-1505 (`parse_spot_inner`), :1308 (`parse_window`), server.rs:11066 (`pull_spot` vendor seat); doc claim at server.rs:779-786 (`param`) | probeapi-5 refuses a repeated key only in the URL query (`request_bounds_refusal` -> `repeated_query_key`). | h-api-3 | low | api | crates/api/src/logs.rs:1031-1044 (`note_request`); default level server.rs:17995-18001, telemetry/src/sink.rs:302 | Every 4xx answer writes one `Warn` `api.request` line, and every 5xx one `Error` line. The served default floor is `Info`, so none of these are filtered, and nothing limits the rate. Any page in the operator's browser can loop `<img src="http://localhost:PORT/x.png">`: the Host is local, so the request is admitted and gets a 404. A cross-site POST gets a 403, which the layer order deliberately routes through `note_request`. Each one appends a line. At roughly 150-200 bytes a line, a few hundred thousand requests roll the whole 64 MiB window (8 x 8 MiB) and erase the pull/sweep evidence. assets.rs `note_missing` names this exact risk ("A scanner walking a wordlist would write a line per probe and roll the run's own beginning out of the sink's 64 MiB window — evidence destroying itself, which is the shape D-0072 forbids") and limits its own line to powers of two. But `note_request` writes an unthrottled line for the same 404 anyway, so that protection does nothing. docs/06-limits.md does not state it. | From the code: `let level = if status.is_server_error() {Error} else if status.is_client_error() {Warn} else {Debug}` followed by an unconditional `telemetry::emit`. `log_level_from(None)` returns `telemetry::Config::new(dir)`, whose `min_level` is `Level::Info` (sink.rs:302). The `admitted()` layer order (server.rs:15919-15938) puts `note_request` outside `same_origin_writes_only`, so 403s are logged. Not measured on a running server. | Apply the same power-of-two summary (or a per-status-class token bucket) to 4xx `api.request` lines, keeping the running count on the line. Or log 4xx at `Debug` except the refusal classes the operator must see (403, 414, 431, 400 from request bounds), and summarise those. State the bound in docs/06-limits.md. |
