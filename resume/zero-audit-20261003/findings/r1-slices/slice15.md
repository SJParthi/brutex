# slice15 — 1 finding

## F1 [medium] A failed `body.bin`/`complete.bin` write leaves a partial file that blocks every retry of that identity for good (11 Boolean/index-stop namespaces)
- where: crates/cli/src/boolean_candidate_persistence.rs:189-212 (`write_or_equal`), called from :119 (`prepare_in_namespace`, body) and :74 (`Pending::finish`, receipt)
- what: `write_or_equal` opens the target with `create_new(true)` and then runs `file.write_all(body).map_err(display)?` (:192). If that write fails, for example ENOSPC or EIO on a large catalog body, or the process is killed during the write, the error goes back through `?` and leaves the partial file where it is. Nothing truncates or removes it, and no caller does either. `grep body.bin` over cli/src finds only reads (:52, :148, boolean_observation_file.rs:63). The identity, and so the directory `<root>/<namespace>/<identity_hex>/`, is deterministic for a rerun:
  - Boolean admission: `identity(statistics, policy, max_bytes)`, boolean_admission_v1.rs:141-152.
  - Boolean candidate catalogs: the campaign predeclares them and requires the computed identity to equal that prediction (boolean_campaign.rs:170-179, 589-591).

  On the retry, `create_new` returns `AlreadyExists` (:204). `read_exact(path, body.len())` then returns the shorter prefix, which differs from `body`, and the call refuses with "Boolean evidence already exists with different or incomplete bytes; history preserved" (:205-206). No `complete.bin` was ever written, so this partial file is not history. Nothing has trusted it. Even so, it refuses the exact rerun every time. This breaks CLAUDE.md §3 rule 5 ("Reruns are safe") and leaves a transient failure as a permanent one. The same path serves every namespace in `known_namespace` (:14-33): boolean-candidates/statistics/admission/oos/qualification, index-consistency and the five index-stop namespaces (callers: boolean_candidate_v1.rs:323, boolean_statistics_v1.rs:191, boolean_admission_v1.rs:117, boolean_oos_v1.rs:278, boolean_qualification_v1.rs:158, index_stop.rs:401, index_stop_qualification.rs:680, index_stop_source_context.rs:321/391, index_stop_vix.rs:406, index_consistency_store.rs:230). In a campaign, the wedged catalog makes its rung Refused on every resume (boolean_campaign.rs:478-496), and later rungs cannot run past it.
- evidence (trace): first run, `prepare_in_namespace` → `write_or_equal(dir/body.bin, body)` → `create_new` Ok → `write_all` Err(ENOSPC) after k < body.len() bytes → returns Err, and body.bin holds k bytes. Rerun with the same inputs gives the same identity and the same `directory_path` (:96). Then `owner.lock` already exists (:107), `Flock::try_lock` succeeds (the previous process is gone), and `write_or_equal` hits `create_new` → AlreadyExists (:204). `read_exact` reads k bytes (≤ max), and k bytes != body (:205), so it returns Err. This repeats on every rerun, and no code path deletes or truncates body.bin. complete.bin (:74) behaves the same way if its 112-byte write is torn.
- fix: in the `Ok(mut file)` arm, any failure of `write_all`/`sync_all`/the length check should `remove_file(path)` (or `set_len(0)` and remove) before it returns the error. Alternatively, write to `body.bin.tmp` and `rename` into place after `sync_all`, then sync the directory, so `AlreadyExists` can only ever see a complete file. Also handle a prefix explicitly in the `AlreadyExists` arm: while `complete.bin` is absent and the owner lock is held, a strict prefix of `body` can be truncated and rewritten, the same way admission_store's D-1630 completes an orphan prefix.

## Known, still present
- W2-cli1-4 / D-1630 (admission_store.rs:1013-1070, :1630-1636): the fix covers only a whole-record prefix. The `write_decisions` rustdoc says one buffer means "a kill can no longer stop between records of one call". For a multi-page `write_all`, though, Linux `generic_perform_write` stops at a page boundary when a fatal signal is pending and returns a short write, and a power loss can also leave a non-544-aligned length. `check_header` (:1630-1636) then refuses that ragged tail at every open, read-only included, and no retry path can repair it. The ledger stays wedged for a non-record-aligned tail. Truncating a ragged tail back to the last whole record, only when the tail lies past the last completed block, would close it. The same reasoning applies on a smaller scale to the 1536-byte V4 lineage pair write (anchored_search_lineage_v4.rs:953-958 comment, :1615-1627 refusal).
