## §A — W2-cli7-2: a strictly cheaper `ledger-v6-replay` (and `ledger-v6` rerun)

### What the route costs today
`replay_route` (`ledger_v6.rs:708-759`) calls the full `run_route` (`:306-425`). For each of 8 rungs × 2 families it runs:
- the strict load;
- `CandidateUniverseProductionSourceV1::new` (column builds);
- `anchored_search_v4` (`step3_orchestrator.rs:3218`: a walk-forward Search V4 run, **before** any reuse decision);
- `produce_candidate_universe_v1`: the Apriori sweep at `candidate_universe.rs:2868` plus a grid expansion with `materialize` per cell;
- the receipt-last appends, where reuse is first decided.

Per rung it then runs `commit_stored_population_v6_route`:
- Observation and Statistics V2/V3, including B = 1,000-draw bootstraps;
- Admission V4, Finalization V4, Population V6, Execution V4 and Selection V6, each recomputed before its append decides Reused.

### Why O(1) is impossible
Reuse is meaningful only if the inputs are the same bytes. That needs the strict, checksum-audited load and its data digest: 16 loads, each O(M + B + source bytes). The OOS witnesses are new work.

### The key fact that makes a cheaper replay possible
The Candidate `universe_id` is computable **before the sweep**.
- `produce_candidate_universe_v1` builds `identities` (`:2791`) and the descriptor (`:2792-2804`, which calls `derive_universe_id` at `:5692`) before `run_prepared_population_by_reporting` (`:2868`).
- The id binds data_digest, feed, source commit, vocabulary, the evaluation policy including the ladder (`min_hits`, ceiling, pair budget), both exit grids, calendar and daily policy, the signal and execution streams, and both column digests.
- Selection V6 blocks encode both families' `candidate_universe_id` and `candidate_completion_digest` (`selection_v6_source.rs:476-482`).

### Plan
1. **Route manifest (new, append-only, D-entry required).** At the end of each rung in `run_route`, after `render_selection`, append one fixed-stride sealed record to `<rung root>/route-manifest-v1.bin`.
   - **Key:** `blake3(domain ‖ rung ‖ nifty universe_id ‖ banknifty universe_id ‖ admission-policy digest ‖ ranking-policy digest ‖ long/short exit-policy digests ‖ statistics procedure (draws, seed, block) ‖ the bounds digests ‖ verb version)`.
   - **Value:** the Selection V6 identity, the Execution V4 completion id, and every `StoredPopulationV6SummaryV1` field `render_route_summary` prints (decisions, counts, terminals, draws/seed/block, admission_block, statistics_authority, ordered_candidates, both universe ids).
   - It is a new file only: no existing format, identity or report byte changes. The `fixed_tail` writer gives the crash and rollback semantics, as for the other ledgers.
2. **Short-circuit probe in `replay_route` and `ledger_v6`.** For each rung:
   - run the two strict loads, which are kept;
   - `resolve_stored_execution_v1` (exit grids, O(E));
   - `CandidateUniverseProductionSourceV1::new` (column builds; the sizing column from D-2103 is the same build, so reuse it: G4-3);
   - compute the descriptor and universe ids **without** `anchored_search_v4` or the sweep: add `fn universe_id_before_sweep(source, ladder) -> [u8;32]`, factored out of `produce_candidate_universe_v1:2790-2804`;
   - compute the key and look it up in the manifest.

   Every rung hit means the short-circuit applies. Any miss means today's full `run_route`. A miss is not a failure; it is noted in telemetry and the report text is unchanged. A corrupt manifest record **refuses**, because CLAUDE.md §4 forbids a fallback that hides a failure.
3. **Rehydrated selection.** Read the Selection V6 record by identity with the existing verified decode (`selection_v6_read.rs`: magic, version, identity and seal under a shared lock). Require that the record's two `candidate_universe_id`s equal the computed ones. For each stored winner (≤ 25 per rung, ≤ 200 per replay):
   - evaluate that winner's exit grid (mask, side) over the loaded execution series;
   - `ResolvedExitGridV1::classify_coordinate` (`runner/src/exit_grid_policy.rs:2619`) gives the opaque `ExecutionDispositionV1`, with the chosen coordinate read from the Candidate/Execution row;
   - **require** `disposition_digest == winner.disposition_id` and `selected_exit_digest == winner.selected_exit_digest`. A mismatch refuses.
4. **One trait for Global Replay V4.** `AllRungSelectionV6` should accept either `CommittedStoredSelectionV6` or the new `RehydratedSelectionV6`, through a crate-private trait with `snapshot()` (identity, envelope, winners) and `stored_oos_witnesses()`. The rehydrated type builds the OOS cohort from the loaded context and the resolved grids, exactly as `stored_post_training_oos_cohort` builds it from the retained context, and mints over one fold per family (D-1684). `commit_stored_global_replay_v4` is unchanged, so its bytes and publication id are unchanged.
5. **Report bytes.** Render the gate census and strict-config lines as today; they depend only on the request. Render `render_selection` from the stored winners, with action "reused", which is what a full-route rerun prints. Render `render_route_summary` from the manifest value.

**Cost after:** 16 strict loads, 16 column builds and execution projections, 8 manifest probes, 8 Selection-record reads, ≤ 200 winner grid evaluations, plus the OOS work. **Removed:** 16 sweeps, 16 Search V4 runs, 16 full grid expansions with per-cell materialize, 8 bootstraps, all Admission/Finalization/Population/Execution recomputation, and every full-ledger reopen on that path. That includes the Candidate ledger at the store root, which is O(R_total) each time.

**Staleness is still detected.**
- The strict guards (`RangeGuard::require_current`) stay held through the replay.
- The data identity is re-derived from the bytes: a different byte gives a different universe id, so the manifest misses.
- A different binary gives a different `source_commit_digest`, so the manifest misses.
- Sealed Selection and manifest records refuse corruption.
- The rebuilt dispositions must equal the sealed digests.

Today it accepts only a live, re-proved chain. `selection_v6_read.rs`'s module doc says a stored record "is not a fresh Selection V6 capability", and that sentence would need amending.

## §B — W2-cli11-2: O(1) Finalization V2 lookup

**Today.** Each lookup takes the shared lock and runs `require_unchanged`:
- the root directory generation;
- the lock file `file_generation`, which hashes the lock file;
- the data `file_generation`, which runs `hash_file_bounded` over the whole data file (`:2882`, `:2929-2966`).

**Plan.**
1. Add `require_platform_unchanged()`. It compares length and `PlatformGenerationV2` (dev, ino, m/ctime ns) of the held and named files against the cached `FileGenerationV2.{len, platform}`, and the root directory generation. These fields already exist; it does no hashing.
2. In `reopen_structural_receipt`, after that check, re-read the two records the cached receipt names:
   - Data at `first_physical_record`;
   - Completion at `first_physical_record + rekey_count + 1`.

   `read_record_at` is fixed stride. Require `digest(data_raw) == data_record_digest` and `digest(completion_raw) == completion_record_digest`. Reuse the scan's own digest helpers, as `structural_receipt_from_block` computes them. That is two record reads and two record-sized hashes: O(1), independent of `rekey_count` and of file size. An absent id returns `Ok(None)` after the metadata check.
3. Keep `scan`'s closing `require_unchanged()` content hash at open; that is the cold check.

**What is no longer seen per lookup:** a same-length rewrite, with every metadata field equal, of bytes this lookup does not return. That means another block, or this block's Rekey rows. Such a rewrite needs a raw device write or a clock change; this is the D-1680/D-1681 residual, UNVERIFIED as reachable. Those bytes are still checked by their own lookups, by the dormant `authenticate_structural_receipt` (the full block), and by the next open.

**When the write path becomes live,** apply the same reverify-only-the-block pattern to append (D-1680 shape). Today the append runs at least 8 whole-file hash passes.

**Tests:**
- A `FINALIZATION_FILE_HASHES` counter: 0 across N lookups, and exactly 1 per open.
- A metadata-visible append refuses.
- A replaced data path refuses ("no longer names").
- A Data byte of the looked-up block flipped under a re-measured generation refuses by digest.
- A Completion byte flipped the same way refuses.
- An absent id returns `None`.
- A flip in a different block is not seen by this lookup but is refused by `open_read`: this documents the limit.

**Docs:** rustdoc `:1174-1178` and `:1426-1436`; the chapter bullet `06-limits.md:15392-15399` becomes "O(1): metadata generation + two fixed records". Update the doc-pin test.

## §C — W2-cli11-3: O(1) Observation V1/V2 lookup and a one-scan append

**Today.** Each lookup reads the whole file into a `Vec` and blake3-hashes it (`:2353`, `:3625`): O(B) time and O(B) memory. The only production use is the append door's fresh reopen (`:2468-2490`, `:3349-3373`). That door costs:
- the writer's open (read + hash + scan);
- `append_data`'s `require_unchanged` (read + hash);
- `refresh_snapshot` (read + hash);
- a fresh `open_read` (read + hash + scan);
- `reopen_audit` (read + hash).

That is about 5 whole-file passes plus 2 scans.

**Layout facts.**
- An authority is a contiguous Data/Completion pair: Data at physical `2·seq`, Completion at `2·seq+1` (`scan_authority_file:2672-2700`; V2 `:3804-3809`).
- The stride is 512 B in V1 and 1,024 B in V2.
- The audit carries `record_sequence`, `data_record_digest` and `completion_digest`. A V1 handle **holds its lock for its whole life** (`lock_file: Flock<File>`, `:2101-2104`), so no cooperating writer can append under a reader.

**Plan.**
1. `require_unchanged` for **lookups** becomes metadata-only. It is the existing pair of `require_observation_generation` calls on lock and file (len, dev/ino, m/ctime ns; already stat-only, `:2757-2800`), with no `read_bounded_*`.
2. `reopen_audit(id)`:
   - after the metadata check, get the cached audit;
   - `pread` 2 × stride at `HEADER + stride·2·seq`;
   - decode both records (seal-verified in `decode`);
   - check `completion.record_sequence == seq` and `completion.validate(&data)`;
   - require `audit_of(&data, completion) == cached`.

   That is O(1) I/O and hashing. The returned bytes are fully re-verified.
3. Append door: replace drop + `open_read` + `reopen_audit` with `reverify_committed(&committed)` on the writer handle, the D-1680 shape. It checks:
   - the metadata generation;
   - physical length == `HEADER + stride·2·(seq+1)`;
   - a re-read and re-decode of the new pair, compared with the expected audit.

   `append_data_with`'s pre-append `require_unchanged` becomes metadata plus a re-verify of the previous tail pair. That catches a torn or rewritten tail before appending onto it, as the store does in `verify_old_tail_before_reseal`. `refresh_snapshot` re-measures the metadata generation only.
4. Keep `snapshot_digest` and the whole-file hash at **open** only.

**Cost after:** lookup O(1); append = one open, O(B) once, plus O(1).

**Not seen per lookup:** an equal-metadata same-length rewrite of *another* authority. That authority's own lookup catches it, and so does the next open. This is the residual D-1681 already accepted for the Pre-Admission page.

**Tests:**
- A `READ_BOUNDED_CALLS` counter: 0 across 10 lookups; 1 per append door (the writer's open).
- A byte flip in the looked-up Data record under a re-measured generation refuses with "seal".
- The same for a Completion byte.
- A metadata-visible write refuses with "changed after open".
- A replaced file refuses ("no longer names").
- A flip in a *different* authority is not seen by this lookup but is refused by that authority's lookup and by `open_read`: this documents the limit.
- One append door runs exactly one scan.
- A foreign append between the writer's commit and the reverify refuses.

**Docs:** rustdoc `:2225-2238` and `:3520-3533`; §157, §161 and the chapter bullet `06-limits.md:15386-15391`. Rewrite `observation_lookups_still_hash_the_whole_file_and_say_so` to pin the new shape: no `read_bounded_authority_file` in the lookup path.

## §D — W2-cli12-1: one full Statistics V2 scan per append, and per rung

**Today**, per rung:
- writer open: scan with every stored bootstrap rerun, plus 2 whole-file hashes in `file_generation`;
- `append_locked`: `require_unchanged` (2 hashes), the write, `validate_complete_block` of the new block, then `file_generation` (2 hashes);
- drop, then a fresh `open_read`: a full scan plus 2 hashes;
- `reopen_audit` through `with_shared_lock`: 2 × `require_unchanged`, which is 4 data hashes (G4-1);
- the orchestrator's third `open_read` for the Admission V3 reader (`step3_orchestrator.rs:2557`).

**Plan (no byte or identity change).**
1. **Reverify through the writer's handle.** Add `fn reverify_committed(&mut self, committed) -> Result<PopulationStatisticsV2ReopenAudit>`. Under the shared lock it runs:
   - `require_unchanged()`. This is a **content** generation here, so it is stronger than a fresh scan at detecting byte changes since the append.
   - Physical record count == `audit.first_record + block_record_count`, for Written.
   - A re-read of only the committed block: `validate_complete_block(&mut self.data_file, audit.first_record, &audit.manifest)`. It is the same function the fresh scan uses, so the audit is bit-identical.
   - The index entry == the re-validated audit. For Written, the block must be the last one in the file.

   `append_population_statistics_v2` becomes open_writer → append → reverify, and **returns the handle** together with the commit.
2. **Reuse the handle as the Admission V3 reader.** Change `PreparedObservationStatisticsV2::append_and_reopen` to return `(commit, PopulationStatisticsV2Ledger)`. `prepare_admission_statistics_projection_v3` then takes that ledger instead of calling `open_read`. This is safe at the API level: `append`, `append_locked` and `open_writer` are private, so a returned writer handle cannot write from outside the module.
3. **Staleness.** Between the writer's scan and the append, `append_locked`'s content-hash `require_unchanged` refuses any byte change. After the append, `reverify_committed` re-hashes. Each later projection read runs `with_shared_lock`, which re-hashes. No byte change the fresh reopen could see goes unseen. What the fresh reopen added was re-running validation on unchanged bytes the writer had already validated; determinism makes that redundant.
4. **Contract wording.** D-1682 rejected this because about twenty rustdoc items say "freshly reopened". The value is the same audit, re-read from disk through a content-current handle. A new D-entry should redefine "freshly reopened" as "re-read and re-validated from disk under a current generation", as D-1680 did for Candidate, and update those rustdoc items.

**Cost after:** one scan per append, and per rung in production (today three), plus 2 × O(new block). Cumulative O(A²) block validations with constant 1, down from 3.

**Further option (contract decision, not recommended without one):** a sealed "verified prefix" sidecar `{prefix_len, content digest, source-commit digest}` would let `scan` skip bootstrap recomputation for byte-identical, already-verified blocks. The file is already content-hashed at open. This would remove the O(A) bootstrap reruns per open. But an adversary with write access could then plant a re-sealed, semantically wrong block, because the seals are unkeyed. That is why it is only listed here.

**Tests:**
- Replace `one_append_runs_two_full_scans_as_section_154_states` with `one_append_runs_one_full_scan_and_rereads_only_its_block`: `STATISTICS_SCANS == 1` for written, reused and orphan-resume.
- A new `BLOCK_VALIDATIONS` counter equals A + 2 per written append.
- The orchestrator's `commit_stored_observation_statistics_v2` runs `STATISTICS_SCANS == 1` for the whole step.
- Reverify refusals, mirroring LBE-02: a foreign appended byte gives "changed after population-statistics open"; a flipped record under a re-measured generation is refused by `validate_complete_block`; a physical count mismatch refuses; an index miss refuses.
- An oracle test: the returned audit equals an explicit `open_read(...).reopen_audit(...)`.
- Update the source-shape assertions in `section_154_states_…`: exactly one `open_writer(` and no `open_read(` in the door.

**docs/06-limits.md §154 (`8155-8163`):** replace "runs two full opens … The step-3 orchestrator then opens the root once more" with the one-scan bound and the handle reuse. Keep "A appends … O(A²) block validations" with the corrected constant.
