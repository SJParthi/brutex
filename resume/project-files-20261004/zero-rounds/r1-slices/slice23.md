## F1 [medium] Admission V3 (live) is permanently stuck after any mid-block failure: a partial whole-record decision orphan is never completed
- where: crates/cli/src/population_admission_v3.rs:3986-3990 (append loop, one `append_raw` per decision), :4567-4594 (`append_with_rollback` truncates only the record that failed), :3699-3723 (scan accepts a partial trailing block as `self.trailing`), :3981-3983 + :4071-4079 (`complete_trailing` requires `trailing.decisions == prepared.decisions`, which means ALL N decisions). Live caller: crates/cli/src/step3_orchestrator.rs:1088 `commit_population_admission_v3_exact_grid`.
- what: `append_locked` writes the N decisions of a new block one record at a time and syncs them only after the loop. Two reachable events leave k whole decisions with 0 < k < N on disk and no Completion:
  (a) a write error (ENOSPC/EIO) on decision k. `append_with_rollback` truncates back only to the start of record k, so records 0..k-1 stay;
  (b) a process kill or power loss between two `append_raw` calls.
  On the next open, `scan` validates those k records through `validate_trailing_decisions` and stores them as `trailing`. The exact rerun then reaches `complete_trailing`, which refuses because `trailing.decisions != prepared.decisions` (k != N), with "Admission V3 trailing block … is not exact retry …". Any other block hits the same branch first, because `append_locked` checks `trailing` before it appends anything. History is never rewritten, so the V3 ledger cannot take any further append, and nothing in the code can recover it.
  V4 in the same slice handles this exact case: population_admission_v4.rs `append_locked` compares the stored prefix and appends the missing suffix. Base Evidence V2 does too: population_base_evidence_ledger_v2.rs:1200-1227 accepts `orphan.record_count <= offered` and calls `compare_prepared_prefix`. Only V3 requires the whole orphan.
  The known lists say "Whole-record orphan prefixes are recovered" (c4b W2 row). For V3 that holds only for a FULL orphan of N decisions, not a partial one. C4-CLI-05-01 / docs/05-decisions.md:44762 (W2-cli10-3) say the rollback fix keeps committed authority readable. That is true, but the ledger still cannot take an append. The only test of the rollback (`a_partial_append_error_truncates_back_and_committed_authority_stays_readable`, :6646) injects the error into a lone extra record after a complete block, never part-way through a multi-decision block.
- evidence: the module's own test pins the refusal. `partial_orphan_corruption_reserve_and_lock_bytes_refuse` (:6365-6386) writes decision 0 of a 4-decision prepared block, reopens the ledger with `open_write` (this succeeds, so the partial orphan is accepted structurally), then runs `assert!(partial_ledger.append(&prepared).is_err())`, i.e. the exact retry of the same prepared block is refused. A probe run of that test (`cargo test -p cli --lib partial_orphan_corruption_reserve_and_lock_bytes_refuse`) was killed (exit 144) before it compiled, so no output was captured. The evidence is the test source plus the trace below. Trace for (a): prepared block N=4 → `append_locked` → loop iteration 2 `append_raw` returns ENOSPC → `set_len(end)` removes only record 2 → returns Err → the file holds decisions 0 and 1 → rerun: `scan` sets `trailing{decisions:[d0,d1]}` → `complete_trailing` sees `[d0,d1] != [d0,d1,d2,d3]` and returns Err. Every later run does the same.
- fix: copy the V4/Base rule into `complete_trailing`. Require `trailing.decisions.len() <= prepared.decisions.len()`, `trailing.block_id == prepared.source.block_id` and `prepared.decisions[..k] == trailing.decisions`, then append `prepared.decisions[k..]`, sync, and append the Completion. Add a test that injects the write error at decision k in 1..N-1 and asserts that the exact rerun is `Written`. Alternatively, roll the whole block back to the pre-block length on any error in the loop, not just the failing record. That covers (a) but not (b).

## F2 [low] Base Evidence V2 `min_win` rustdoc and a 30-line comment still describe D-0595's bracket rule, which D-0602 reversed; the code does the opposite
- where: crates/cli/src/population_base_evidence_v2.rs:373-383 (field rustdoc on `TradeAggregatesV2::min_win`), :1057-1087 (comment block in `fold_trade_rows`); code at :1093-1094.
- what: the field doc says `min_win` is "The smallest win that EXCEEDED its own execution bracket — D-0595", and that "Zero now carries two meanings — nothing won, or nothing won by more than its own pricing uncertainty". The comment block says "a win counts toward `min_win` when it EXCEEDS its own bracket, and is a scratch otherwise". The code is `if row.worst > 0 && (min_win == 0 || row.worst < min_win) { min_win = row.worst; }`, which has no bracket test. That is D-0602 (docs/05-decisions.md:35723), which reverses D-0595 and names this function as one of the four sites it corrected. docs/04-invariants.md AS-12/AS-13 were rewritten for D-0602, but this rustdoc was not. The only correction is one trailing line at :1090-1091.
  This matters because `min_win` is the numerator of `worst_reward_risk_ppm`, the mandatory `min_worst_reward_risk_ppm` admission gate (the operator's 3:1 rule). A reader following the field doc would conclude the gate uses the bracket-filtered floor, the inflated reading D-0602 calls "five times better". The "zero carries two meanings / no scratch_wins field" reasoning is now false: zero means only "no trade won".
- evidence: code :1093 vs doc :373 and comment :1074-1075, side by side above. D-0602 text: "`population_base_evidence_v2::fold_trade_rows` … were corrected together".
- fix: rewrite the field doc to "smallest pessimistic (worst-reading) P&L over trades with `worst > 0` — D-0602, reversing D-0595". Delete the "two meanings / scratch_wins" paragraph and the D-0595 comment block, keeping a one-line pointer to D-0602. The same stale D-0595 text appears outside this slice at crates/runner/src/grid.rs:6165 and crates/cli/src/institutional_evidence.rs:1633, and should get the same edit.
