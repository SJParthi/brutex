## F1 [medium] The masters page, its module docs and a test all say a refresh needs a restart, but the refresh already reloads the universe
- where: crates/api/src/mastersrun.rs:21-33 (module doc), :648-655 (`status_json` doc), :808-813 (`page_html` footer), :1520-1528 (test `the_page_says_a_restart_is_required_rather_than_pretending_otherwise`); crates/api/src/lib.rs:103-106
- what: Each of these says `Site::load` parses the masters once at startup, that "there is no reload path", and that the operator must restart after a refresh. The footer on the HTML page says: "A refresh writes new bytes to disk and does <b>not</b> reload the parsed universe ... Restart the server after a refresh". The code does the opposite. `refresh` calls `reload(&site, &dir)` at mastersrun.rs:627. `reload` (:381) calls `Site::reparse` (server.rs:5439), which swaps a fresh `Parsed` into `site.parsed` with a new `at` and `generation`. The JSON then answers `"restart_required":false` (:638). `reload`'s own doc at :362-369 says this is "what makes a refresh mean anything", and that `restart_required` "was hardcoded `true` here for two commits". So the module disagrees with itself. The test pins the stale sentence: it asserts the page contains "restart is required" and "Restart the server". It passes only because the wrong text is still there, so it cannot catch this drift. An operator reading the page restarts a server that has already reloaded.
- evidence: trace. mastersrun.rs:627 `let reloaded = reload(&site, &dir);` → :382 `site.reparse(dir)` → server.rs:5489-5498 `*held = Parsed { read, at: parsed_at, targets, generation }`. The footer string is at mastersrun.rs:808-813, and the test asserting it is at :1520-1528. lib.rs:105 says "`Site::load` parses the masters once at startup with no reload path, so this also answers whether a restart is required."
- fix: Rewrite the module header, the `status_json` doc, lib.rs:103-106 and the page footer to say that a refresh re-parses through `Site::reparse`, and that a restart is needed only when the reparse is refused (`reloaded:false`) or `/masters/status.json` reports `newer_than_parse`. Change the test so it asserts the page does NOT tell the operator to restart after a successful refresh.

## F2 [low] The three-part date fields still accept a signed piece, so D-0905's refusal can be bypassed
- where: crates/api/src/ingest.rs:1292-1299 (`parse_day_field`'s `pad` closure), compared with :1225-1229 (`parse_day`'s digit-only check, D-0905)
- what: D-0905 made `parse_day` refuse any byte other than an ASCII digit or `-`, so that `2024-+8-+6` is no longer read as 2024-08-06. `parse_day_field` builds its ISO string from `from_y` / `from_m` / `from_d` by running each piece through `text.parse::<u16>()` and re-formatting it zero-padded. Rust's integer `FromStr` accepts a leading `+`, so `+8` becomes `08` and the sign is gone before `parse_day` checks digits. The same padding accepts over-wide pieces such as `0002024` / `0008` / `00006`. Both are the "strict on shape" violation D-0905 recorded, reached through the date-picker field path that every spot, F&O and recovery form uses (`parse_window` → `parse_day_field`).
- evidence: a probe I ran (temporary `crates/api/tests/zz_probe_slice13.rs`, since deleted):
  ```
  ISO: Err(DateNotIso { field: "from", got: "2024-+8-+6" })
  TRIPLE: Ok(Day { year: 2024, month: 8, day: 6 })      // from_y=2024&from_m=%2B8&from_d=%2B6
  PADDED: Ok(Day { year: 2024, month: 8, day: 6 })      // from_y=0002024&from_m=0008&from_d=00006
  ```
- fix: In `pad`, return the text unchanged (so the width and digit checks in `parse_day` refuse it) unless every byte is an ASCII digit and `text.len() <= width`. Add `from_m=%2B8` and an over-wide piece to `a_date_field_is_refused_by_name_whichever_way_it_is_wrong`.

## F3 [low] `/audit.json` answers a malformed invocation id or page cursor with 503 "unavailable" instead of 400
- where: crates/api/src/operation_audit.rs:216-222 and :223-259 (`integer` / `parse`), :279-285 (`audit_json`), :29-44 (`read_failure`)
- what: `parse` accepts any canonical positive decimal for `invocation=` and `before=`. Every real id is at least `cli::operation_audit::ID_BASE + 1` (2^63 + 1). `journal::read` refuses ids below that ("ID is outside the durable invocation namespace", cli/src/operation_audit.rs:588-591). `journal::page` refuses `before <= ID_BASE` ("invalid bounded invocation page", :649-650). Neither message carries the BUSY prefix, so `audit_json` maps both to `read_failure(.., busy=false)`, which is HTTP 503 with the body "No audit snapshot was published". A caller error is reported as server unavailability, and a poller that retries on 503 will retry a request that can never succeed.
- evidence: trace. `GET /audit.json?invocation=5`: `integer("5")` = Ok(5) → `Asked::Exact(5)` → `render` → `journal::read(root, 5)` → `5.checked_sub(1<<63)` = None → Err(non-busy) → `read_failure(&why, false)` → `StatusCode::SERVICE_UNAVAILABLE`. `?before=5` takes the same route through `page`.
- fix: In `parse`, refuse `invocation` and `before` values `<= journal::ID_BASE` with the existing 400 path ("audit IDs must lie in the durable invocation namespace"), so that a 503 only ever means the store or lock is unavailable.

## F4 [low] The livejson module doc names `wins` as a structural zero, but the route serves it as a real figure
- where: crates/api/src/livejson.rs:19-26 (module doc) compared with :199-223 (`write_row` serves `"edge_wins": row.wins`)
- what: The header explains why the live view must not judge rows: at `publish_ranked` time "`trades`, `wins`, `pessimistic`, `worst_trade`, `max_drawdown`, `min_win`, `gross_win` and `gross_loss` are all structural zeros". `Row::wins` is not a cell field. It is `scored.edge.wins` (cli/src/frontier.rs:671), filled at publish time from the sweep half. The cell's count is `cell_wins` (:677), and that is the one that is zero there. `write_row` correctly serves `row.wins` as `edge_wins` among "the eight fields that are REAL before the grid runs", and the web reads it as a win rate (web/src/routes/backtest/+page.svelte:7291). So the doc that justifies the route's shape lists a real, served figure as unmeasured. A maintainer following the doc would remove `edge_wins` or report it as zero.
- evidence: trace. cli/src/lib.rs:17866-17873 `publish_ranked` → `Row::of(identity, rank, scored, None, None, rules)` → frontier.rs:671 `wins: scored.edge.wins`, :677 `cell_wins: cell.map_or(0, ..)` (0 because cell = None).
- fix: In livejson.rs:22, replace `wins` with `cell_wins`. Optionally say that `edge_wins` is the sweep's own count and is real at publish time.
