## F1 [medium] docs/02-store-format.md gives the wrong on-disk size for the execution-parameter record (608/640 in the doc, 616/648 in the code), and every field offset after byte 192 is 8 bytes off
- where: docs/02-store-format.md:918, :922-936 (V1 §17 table and offset table), docs/02-store-format.md:1165 (V2 table, `BRUX2PR1` row, which reuses the same codec); rustdoc crates/cli/src/execution_capability.rs:1350 ("Scalar parameter records (640-byte stride)")
- what: CLAUDE.md §10 makes docs/02-store-format.md the authority over the bytes on disk. For `results/execution-parameters-v1.bin` and `results/execution-disposition-parameters-v2.bin` it says payload 608 and stride 640, and that the evaluation-spec fingerprint is 155 bytes at payload offset 192. The code says payload 616 and stride 648, with a 163-byte fingerprint. The code's own comment at execution_capability.rs:68-74 records the widening ("616, NOT 608 … widened 155 -> 163 when the charter gained its ninth non-regular day"), but the document and the path rustdoc were never updated. Every offset in the doc's payload table from 347 on is therefore 8 bytes low: tags are documented at 347 but sit at 355; the counts at 356 sit at 364; and so on up to the reserve, documented at 600 but at 608, and the seal, documented at 608..640 but at 616..648. A reader or external tool decoding these files from the spec would misparse every field after the fingerprint, and would also reject every file as ragged, because (len-24) is not a multiple of 640.
- evidence (trace, compile-time constants):
  - execution_capability.rs:74 `const PARAMETER_PAYLOAD_BYTES: usize = 616;`
  - execution_capability.rs:101 `const _: () = assert!(EXECUTION_PARAMETER_STRIDE == 648);`
  - execution_capability.rs:109 `const _: () = assert!(EVALUATION_SPEC_FINGERPRINT_V1_LEN == 163);`
  - Encoder walk in `ParameterScalarV1::payload` (execution_capability.rs:3033-3089): 6×32=192, +163 fingerprint=355, +9 tag/reserve bytes=364, +6×u32=388, +2×u16=392, +5×u64=432, +2×i64=448, +8×8=512, +3×32=608, +8 reserve=616. `Encoder::finish` requires exactly 616.
  - docs/02-store-format.md:918 `| results/execution-parameters-v1.bin | BRUTXEP1 | 608 | 640 |`, :922 "The 608-byte parameter payload is:", :926 `| 192 | 155 | exact evaluation-spec fingerprint |`, :935-936 `| 600 | 8 | reserved |`, `| 608 | 32 | BLAKE3 seal over payload 0..608 |`; :1165 `| results/execution-disposition-parameters-v2.bin | BRUX2PR1 | 608 | 640 |`.
- fix: update docs/02-store-format.md §17 (table row 918, the "608-byte" sentence, and every offset from 192 on: fingerprint 163 bytes; tags at 355; counts at 364; entry delay 388; forced exit 390; five u64 at 392; ratios at 432; 64-byte block at 448; digests at 512; reserve at 608; seal 616..648) and the V2 row at :1165 to 616/648. Also fix the rustdoc at execution_capability.rs:1350 to "648-byte stride". Add a doc-sync test, like the one core/tests/graph.rs uses for the architecture table, that parses this row against `EXECUTION_PARAMETER_STRIDE` so the next fingerprint widening cannot drift silently again.

## F2 [low] docs/02-store-format.md says the V2 execution-disposition reopen validates "admission marginals", but reopen never reads the admission authority
- where: docs/02-store-format.md:1195-1197; code: crates/cli/src/execution_disposition_v2.rs:2624-2747 (`build_disposition_indexes`) and :2772-2846 (`validate_committed_disposition_block`)
- what: the doc says: "Reopen validates every record and reconstructs the parameter blocks, exact row order, row count, sparse-capability/refusal partition, **admission marginals**, 4×2 matrix and ordered digests before indexing." The only marginal check is `ExecutionCapabilityCompletionV2::require_admission_marginals` (:1070). Its only caller is `PreparedExecutionDispositionsV2::from_ledgers` (:1435), the prepare path. `ExecutionDispositionLedgerV2::open`/`open_read` → `from_files` (:2123) → `build_disposition_indexes` takes only the four V2 files. No `AdmissionAuthorityLedger` or `AdmissionCompletionReceiptV1` is in scope, so the row-totals of the stored matrix are compared only with the rows' own `admission_status` bytes (:2808, :2831-2840). A V2 block whose rows carry admission statuses that differ from the admission ledger therefore reopens and indexes successfully if it is internally consistent: the seals are unkeyed BLAKE3, so a reseal recomputes them. `completion()`, `row()` and `page()` then serve it as committed authority. The doc's claim that reopen proves admission marginals is false. Only internal matrix consistency is proven.
- evidence (trace): `grep -n require_admission_marginals crates/cli/src/*.rs` → only the definition (:1070) and the call in `from_ledgers` (:1435). `build_disposition_indexes` signature (:2624-2629) has four slices: parameters, percentiles, rows, completions. It has no admission input.
- fix: either change the doc to say that reopen proves only internal 4×2 matrix consistency and that admission marginals are proven at preparation (and must be re-proven by any consumer that joins the admission ledger), or add an `open_*` variant or consumer-side check that takes the admission ledger and calls `require_admission_marginals` for each indexed completion.
