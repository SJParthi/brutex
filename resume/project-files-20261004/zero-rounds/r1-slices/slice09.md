# slice09 — 2 findings

## F1 [low] VWAP truth bits compare the close against FLOORED vwap and sigma, so close_below_vwap (53/144) misses real below-VWAP closes and the band "above" bits fire below the true band
- where: crates/indicators/src/vwap.rs:304-310 (`value` = `pv.div_euclid(3v)`, a floor), :518-525 (`close > vwap` / `close < vwap`), :542-555 (band levels from `band_levels(vwap, sigma, k)` built from the floored vwap and floored sigma), :613-616; `known` at :563-585 marks 52/53/143/144 and 146..197 as KNOWN for these same comparisons.
- what: VWAP is a rational `pv/(3V)`. `value()` floors it to whole paisa, and `bits` then tests integer `close` against that floor. When `close == floor(VWAP) < VWAP` the close is strictly below VWAP, but `close < vwap` is false and `close > vwap` is false, so NEITHER bit is set, while `known` says both are evaluable. That is a known-false on a bar where the predicate is true. The error only runs one way: "below" is under-reported and "above" never is. The bands have the same problem, scaled up. `upper_k = floor(V) + k*floor(sigma)` can sit up to `1 + k` paisa under the true `V + k*sigma`, so `close > upper` (146/148/193) can be set for a close that is inside the true band. The doc on `sigma` (:315-356, D-0940) makes sigma exactly `floor(sigma)`, "nothing coarser", but the comparisons that use it are still coarser than the predicates they name. The `side()` doc in trend.rs:1008-1016 treats this equality-bucket case as a defect class.
- evidence: a probe I ran (`crates/indicators/tests/zz_probe_slice09.rs`, now deleted) used the public API. Two bars in one IST session with `Availability::Present`: bar 1 h=l=c=10000 v=1, bar 2 h=10001 l=10000 c=10000 v=1. The true VWAP is (30000+30001)/6 = 10000.1667 paisa and the close of 10000 is below it. Output:
  ```
  value=Some(10000) sigma=Some(0)
  above52=false below53=false above143=false below144=false
  ```
  Band case from the same probe: p2=10001, v2=2 gives `vwap=10000(10000.667) sigma=0(0.471) close=10002 computed_upper3=10000 true_upper3=10002.081 above_band3_bit193=true`. Bit 193 is set although 10002 < 10002.081. This example uses a two-bar sigma that floors to 0, which overlaps the known F-9A6BC3. But the band error needs no zero sigma: every floored `V` and `sigma` loses up to `1 + k` paisa in general.
- fix: compare exactly in integers. `close < VWAP` iff `3V*close < pv`, and `close > VWAP` iff `3V*close > pv` (both fit in i128 under ACC_CEILING). For the bands, compare `(3V*close - pv)^2` against `k^2*(V*p2v - pv^2)` with the sign handled, using the existing `wide_mul` 256-bit compare. Or at least use the floored levels only where rounding cannot change the answer, and leave the bit unknown otherwise.

## F2 [low] `Ladder::with_ceiling` / `Ladder::ceiling` document a PER-LEVEL ceiling, but the ceiling is cumulative across the whole walk
- where: crates/engine/src/lib.rs:1051 ("The same ladder with a different per-level candidate ceiling."), :1070 ("The per-level candidate ceiling this ladder will actually apply."). The code that contradicts them is at :1726 (`admitted.saturating_add(emitted) >= self.ceiling`, where `admitted` is cumulative per :1644). Halt :613-626, `DEFAULT_CEILING` :730-738 and `exhausted` :1689-1714 all say cumulative, and the test `the_budget_is_cumulative_and_a_per_level_cap_would_miss_it` pins cumulative.
- what: these are the only public docs on the knob a caller sets (`cli::whole_machine_ceiling`, per the DEFAULT_CEILING doc). A caller who sizes the ceiling as "the most one level may hold", as these two rustdoc lines say, gets a halt (`Breach::Candidates`) at a depth where no single level came near that size. The halt is loud, so this is not silent. But the public contract misstates what the parameter bounds, and this file's own Halt doc records the per-level vs cumulative confusion as an earlier OOM defect.
- evidence: trace. `continue_walk` :1642-1645 does `progress.admitted += added` for every level. `try_next_level_observing` :1976-1977 calls `exhausted(emitted, admitted, ..)` and refuses when `admitted + emitted >= ceiling`. So one level of 10 candidates after earlier levels admitted 95, with `with_ceiling(100)`, halts at its 5th candidate. That contradicts "per-level candidate ceiling".
- fix: reword both rustdoc lines to "the cumulative candidate ceiling (distinct joined candidates admitted across every level of the walk; singletons excluded)".
