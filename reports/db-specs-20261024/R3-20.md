### 3.6 D-3353 (the state the door recovers from), verbatim from the head

`docs/05-decisions.md` at `e851da1ca`, the entry `### D-3353` (line 67206 onward).

```text
### D-3353 — A GDFL import day's writes are made durable together, before its ledger lines, its census batch and its closing line — 2026-10-15

**Written by AF-07 at the number WP-16 cited** (60 citations under
`crates/`; DB-N25). WP-16's report carried the text; this entry restates what
the code at `079ad4af` enforces.

**Decision.**

1. Every write of a day's files goes to one `store::file::DurableBatch`
   that the day's worker threads share. Nothing written in it is durable
   until `DurableBatch::make_durable` returns, which the import calls when
   the day's last file is filed and before the day's ledger lines, its
   census batch and its closing journal line. A kill at any point leaves
   every month at a commit and the day open, so the next run reads it again.
2. **The unit is `BRUTEX_GDFL_DURABILITY`**: `day` (the default, chosen by
   measurement: `O_SYNC` writes, then one `F_FULLFSYNC` per directory that
   gained a name and one per device), `day-each-file` (plain writes, then
   one `F_FULLFSYNC` of every file) or `each-write` (every writer flushes for
   itself, as before WP-16). Any other word is refused by name, never read
   as the default. The bytes a run leaves do not depend on the durability or
   on the number of workers.
3. **A census batch of n entries is three flushes**
   (`pull::census_store`): all n entries; one write to the slot the batch's
   first commit belongs in; one write to the other slot. At most one slot
   write is in flight, and it never lands on the slot holding the newest
   durable generation unless the other slot already durably holds a newer
   one. Under a power cut a batch is a prefix, not all-or-nothing.
   `docs/02-store-format.md` §11.7 does not state this yet.
4. **A back-fill (D-3350) is not a worker's and not the batch's**: the
   coordinating thread files it after the day's workers are done, outside
   the batch, because the repair's own flushes order a revision before its
   promotion.
5. **The default is weaker than `each-write` against a power cut inside an
   open day** (not a kill): a month torn there is refused by its own checks
   until it is repaired. It also rests on "an `O_SYNC` write counts as
   flushed for one `F_FULLFSYNC` per device", which is **UNVERIFIED**.

**Proven by** `pull`'s `gdfl_import_tests.rs`
(`each_day_is_made_durable_before_its_closing_line`,
`the_durability_unit_changes_no_byte_a_run_leaves`,
`w_workers_build_the_same_store_journal_and_census_as_one`,
`a_back_fill_is_published_outside_the_days_batch_and_leaves_one_workers_store`),
`pull`'s `census_store_tests.rs`
(`a_batch_is_three_flushes_and_one_slot_write_at_a_time`,
`a_torn_write_inside_a_batch_never_leaves_the_census_behind`) and `cli`'s
`gdfl_import_command_tests.rs`
(`durability_is_the_default_or_one_of_its_words`).

```

```text
//!   at its last commit or its new one, exactly as above: what a killed
//!   process wrote is in the kernel, in the order it was written;
//! * no flush is issued per append, per new name or per sidecar record. With
//!   [`BatchFlush::OncePerDevice`] every file is opened `O_SYNC`, so each
//!   write is on the device when it returns, and the batch ends with one
//!   `F_FULLFSYNC` per device (and one per directory that gained a name);
//!   with [`BatchFlush::EveryFile`] the batch ends with one `F_FULLFSYNC` of
//!   every file and directory it wrote;
//! * so nothing is durable until [`DurableBatch::make_durable`] returns `Ok`,
//!   and the caller's unit (the import's day) is not closed until then, so a
//!   unit cut off before it is read again;
//! * a unit read again finds months an earlier process wrote and never made
//!   durable. The store answers them `AlreadyPresent` from the kernel's
//!   cache and writes nothing, so nothing of theirs would be in the new batch:
//!   the caller names each one with [`DurableBatch::confirm_month`], and the
//!   batch then flushes every file of that month for itself, and every
//!   directory down to it, whatever its kind.
//!
//! **What a power loss inside an open batch can leave, said rather than
//! implied away.** Between a batch's first write and its `make_durable` no
//! barrier orders a month's records before its header slot on the drive, so a
//! power cut (not a killed process) can leave a month the batch appended to
//! with its slot on the platter and its records, or its checksums, not. Such
//! a month is not served: its length, its header and its block checksums
//! refuse it by name, and it stays refused until it is repaired; the bars it
//! held before the batch are behind that refusal too. A writer that cannot
//! accept that asks for no batch and keeps the table above.
```

### 7.3 What the header and the doors give a recovery

- Two header slots: `store::format::MAX_SLOTS = 2` (`format.rs:103`), `SLOT_STRIDE` 16,384, a 32,768
  byte header region; commit g goes to slot `g % slot_count`. `Header::read_region` takes the valid
  slot with the highest generation the file's LENGTH supports and falls back to the previous
  generation when the newest slot outruns the bytes; but `BarFile::validated`, which every open
  door calls, then refuses the file `FormatError::CounterExceedsFile` when a slot that still decodes
  claims more records than the generation chosen (`header.rs` lines 40-50, D-0792). So a month torn
  as D-3353 says is refused by every door today. With only two slots, the "last commit whose records
  check out" is at most one generation back by the header alone; a month whose two newest commits
  were both in the open batch has no older slot left, and its block checksums (`.crc` sidecar,
  `BlockChecksum`) are then the only proof of a good prefix. That case is an extreme case to test.
- `store::header::slot_audit(region, file_len) -> SlotAudit` (line 1102) reads every slot without
  choosing, with `SlotState::{Empty, Valid{generation}, Damaged{reason, generation}}` and
  `MonthVerdict::{Clean, Damaged, Reverted, Unreadable}` (D-6240, D-6241: a slot whose checksum
  fails has NO known generation). The ratio bench C-HA-01 already times it at 1x/10x/100x.
- New files and generations: `store::repair::publish` (line 400) writes a revision under
  `<root>/bar-revisions-v1/<n>` (receipt magic `BRXREPV1`, `MAX_REVISIONS` 1,024, written in commits
  of `WRITE_BATCH` 524,288 rows); `store::generation::promote(root, path, symbol_id, revision)`
  (line 419) makes it the served generation. `promote` "must have been published FROM the generation
  served now — its receipt's source header equals the served month's header" and opens the served
  month to check it: a door for a month no door can open must answer how that proof is made,
  without editing `repair.rs`/`generation.rs` (other parts own them). `repair_month` (540) and
  `repair_month_with` (584) need a source to read and merge; `crates/store/REPAIR.md` holds the
  publication protocol.
- R3-16's helpers (merged): `store::safe_open::{open_read, open_read_len, open_read_write,
  name_the_refusal, refuse_linked_store_root}` and `store::staging::create(path) -> Staged`. Use them
  for every new file you create or read.
- SC-4 (merged): a sealed month's writer door answers `StoreError::Sealed{offer: SealedOffer}`;
  "a recovered month is a new raw file and is sealed like any other".
